# Layer4 multi-route precedence: `anyRouteNeedsMore` (T-0713)

```bash
./scripts/layer4-concurrency/precedence.sh              # CaddyUI-shaped config
./scripts/layer4-concurrency/precedence.sh --catch-all  # + a route CaddyUI can't emit
```

This is the third part of the caddy-l4 v0.1.3 delta, and the one
[T-0631](#) deliberately left uncovered. It is a **differential**, not a
pass/fail gate — see [Why this is not `run.sh --prove`](#why-this-is-not-runsh---prove).

## What changed in v0.1.3

`layer4/routes.go` tracked pending routes with a single watermark,
`lastNeedsMoreIdx`. v0.1.3 adds a scan of the per-route status map:

```go
// lastNeedsMoreIdx is a watermark, so a conclusively unmatched route can bury an
// earlier one that is still waiting for data; consult the statuses directly instead
anyRouteNeedsMore := func(before int) bool {
    for i, s := range routesStatus {
        if s == routeNeedsMore && i > lastMatchedRouteIdx && i < before {
            return true
        }
    }
    return false
}
```

and uses it at two sites:

| site | decides | reachable from a CaddyUI config? |
| --- | --- | --- |
| `routes.go:187` | whether a **catch-all** route may match while an earlier route is still pending | **No** — CaddyUI never emits a catch-all |
| `routes.go:238` | whether matching **keeps looping** for more bytes or falls through | **Yes** |

A watermark is one number, so it cannot represent "route 0 is pending **and**
route 1 is decided". The upstream comment names the consequence; this harness
measures it.

## The config under test

Four competing routes on one shared HTTPS port, generated by CaddyUI's own
`buildLayer4ListenerWrappers` via `TestEmitLayer4PrecedenceConfig`
(`internal/server/layer4_precedence_config_test.go`):

| route | matcher | bytes it needs | upstream (sink) |
| --- | --- | --- | --- |
| 0 | `ssh` | 4 | `:22301` |
| 1 | `postgres` | 8 | `:22302` |
| 2 | `rdp` | 19 | `:22303` |
| 3 | `tls` (SNI) | full ClientHello | `:22304` |
| — | pass-through to Caddy's own TLS+HTTP | — | `srv0` |

Each route proxies to **its own labelled sink**, which announces
`LANDED=<label> BYTES=<n> HEX=<…>`. The landing route is therefore *observed*,
not inferred — inference cannot tell "route 2 matched" from "route 0 matched and
its upstream was down", which is why the first design was discarded.

**Route order is creation order, and the operator cannot change it.**
`ListLayer4Proxies` sorts by `(protocol, listen_port, id)`, so for proxies
sharing a port, precedence is decided by which proxy was added first. That is a
CaddyUI fact worth knowing independently of anything caddy-l4 does.

**Each probe is sent in two writes** (`head`, gap, `tail`). Sending the whole
sequence at once usually lands it in one TCP segment, every matcher gets all its
bytes on the first prefetch, no route is ever pending, and both versions agree —
the probe would measure nothing. The split is a real client pattern, not a
contrivance: an SSH client sends its identification string and waits, and an RDP
connection request can straddle segments on a slow link.

## The boundary is the SSH threshold, not the obvious one

Scanning **every** head length 1..19 against both images:

| head bytes | v0.1.2 | v0.1.3 |
| --- | --- | --- |
| 1–4 | rdp | rdp |
| 5–18 | **none** | **rdp** |
| 19 | rdp | rdp |

The boundary is **4 bytes — the `ssh` matcher's threshold**, not the 8 bytes
`postgres` needs. This harness's first hypothesis said postgres and was wrong;
`rdp-split-after-7` exists because it falsified it.

Why 4 is the boundary:

- **head ≤ 4** — `ssh` (route 0) cannot decide either, because `io.ReadFull`
  needs all 4 bytes. Route 0 is itself `routeNeedsMore`, so v0.1.2's watermark
  is left pointing **at** a genuinely pending route, `lastNeedsMoreIdx <
  len(routes)` holds, and matching loops for more bytes on its own. Both
  versions land `rdp`.
- **head ≥ 5** — `ssh` **decides** (the bytes are not `SSH-`). The
  `i >= lastNeedsMoreIdx` branch advances the watermark to 1, each later
  deciding route advances it again, and it reaches `len(routes)` while `rdp` is
  still pending. `routes.go:238` is then false, matching **stops**.

So the route that buries the pending one is **`ssh` at index 0** — the earliest
route, not a later one. `anyRouteNeedsMore` repairs it by scanning
`routesStatus` instead of trusting one number.

**v0.1.2 is not timing out.** The dropped connections close at ~301 ms, when the
tail arrives — not at the 3 s `matching_timeout`. Matching concluded and left
nothing to run. A harness that only watched for timeouts would miss this.

## What this means for a host that enables shared-port Layer4

Read before depending on it; none of this is a reason to block a rollout, and
v0.1.3 is the better behaviour in every row above.

1. **On v0.1.3 a split first packet reaches the route its protocol says it
   should.** On v0.1.2, with ≥2 shared proxies on one port, a client whose first
   packet arrives in pieces could be **dropped** (CaddyUI-shaped config) or sent
   to **the wrong backend** (catch-all present). v2.68.12 and later carry
   v0.1.3, so the fleet is on the repaired side.
2. **The catch-all case is the one with a security flavour.** "Dropped" fails
   closed; "landed on the catch-all" is a connection reaching a backend chosen by
   a matcher that never got to finish. CaddyUI cannot emit a catch-all, which is
   asserted in the emit test rather than assumed — if a future `MatchKind` ever
   emits a bare route, that test fails and this analysis must be redone.
3. **Precedence is creation order.** Two shared proxies whose matchers can both
   plausibly claim a packet resolve by `id`, i.e. whichever was added first. The
   UI offers no way to reorder them.
4. **One row moved the other way.** `junk-5-bytes-then-nothing` went from
   catch-all (v0.1.2) to dropped (v0.1.3). For bytes that match nothing and a
   client that sends no more, v0.1.3 waits for the pending matchers and then
   drops, where v0.1.2 handed the connection to the catch-all. If a deployment
   *wants* a catch-all to absorb unrecognised traffic, v0.1.3 absorbs less of it.
   This is the one row where "better" depends on intent, which is exactly why
   this harness reports instead of asserting.

## Why this is not `run.sh --prove`

`run.sh` (T-0631) tests two defects with a right answer: a leaked TLS
ClientHello (#483) and a deadlocked reload (#482/#492). Both are wrong on any
reading, so that harness demands the fixed image **pass** and the buggy image
**fail** — a green run on the buggy image would mean it proves nothing.

Precedence has no such anchor. Until the intended behaviour is established,
"the catch-all won" is not self-evidently worse than "the pending route won", and
asserting one would bake today's guess into a gate. So this script records the
table per image and prints the differences.

It still fails on what is broken under **any** version:

| exit | meaning |
| --- | --- |
| 0 | the differential ran; differences may have been found and printed |
| 1 | a route answered for a protocol it does not match, or `--strict` and a probe reached nothing |
| 2 | the harness could not run — **not** a pass |

Exit 2 is separate for the same reason as in `run.sh`: a harness that cannot
start must not look like one that ran and found nothing. The sink refuses to
start unless all five ports bind, because a sink that failed to bind would make
every connection to that route read as a routing decision.

Each probe runs 3× and a landing that varies is reported as `UNSTABLE:a/b/c`
rather than sampled once. If precedence for some bytes were timing-dependent,
recording one sample would turn a flake into a documented fact.

## Still not covered

- **`tls` (SNI) as the pending route.** All four diverging probes leave `rdp`
  pending. A TLS ClientHello split mid-handshake would exercise route 3, and the
  `tls` matcher reads far more bytes than the others, so its window is wider.
  Not built here because an on-demand-issuance handshake needs the TLS client
  machinery the T-0631 driver already has, and splicing the two drivers is more
  work than this card's question needed.
- **More than one pending route at once.** `anyRouteNeedsMore` scans for *any*
  pending route; a config where two are pending simultaneously would test the
  scan's bounds (`i > lastMatchedRouteIdx && i < before`) rather than just its
  existence.
- **UDP / packet-connection wrappers.** v0.1.3 also added `packet_conn_wrappers`
  with their own matching and an `idle_timeout`. CaddyUI generates TCP listener
  wrappers only (`validateLayer4Shared` rejects UDP for shared mode), so this is
  out of scope until CaddyUI offers it.
